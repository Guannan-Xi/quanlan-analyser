**文档状态**：对外说明草案，待确认

**更新日期**：2026-07-27
**文档用途**：向外部读者说明 QLanalyser 要解决什么问题、如何解决、目前做到哪一步、长期方向。实现细则、验收清单、权限规则与成本测算见配套附录文档。

## 1. 要解决的问题

一个典型的脑电研究课题组，工作流大致是这样断裂的：采集设备导出的原始数据存在实验室某台电脑上，预处理靠研究生自己写的 MATLAB 脚本，统计分析换成 Python，出图又回到 MATLAB。参数记在各人的记事本里，中间结果散在不同命名规则的文件夹中。

半年后论文返修，审稿人要求补一组对照分析。此时原始数据还在，但当初用的滤波频段、剔除了哪些坏导、ICA 去掉了哪几个成分、跑的是哪个版本的工具箱——已经无法完整复原。做这份分析的学生可能已经毕业。

这不是个别现象，而是脑电研究里可复现性问题的常见形态：**分析能力存在于个人环境和个人记忆中，而不是存在于可交付、可追溯的系统里。**

课题组还要额外承担与科研无关的成本：维护 Python/MATLAB/GPU 环境和依赖版本，处理工具箱之间的兼容问题，反复制作格式一致的图表。医院科研团队在此之上还有去标识化、访问控制、审计和数据保存周期的合规要求。

QLanalyser 要做的，是把这条链路——从原始记录到质量控制、预处理、分析、人工复核、结果交付、复现材料——收进一个统一的产品，让每一步的输入、参数、软件版本和输出之间保持可追溯关系。

平台的价值不在于包装某个开源算法（这些算法本身多数是公开的），而在于把这条流程做成**可审查、可复核、可复现、可规范交付**的产品。

## 2. 产品定位与核心流程

QLanalyser 是面向神经科学研究的综合科研平台，长期覆盖电生理分析、电场仿真与科研数据保护。

用户的主流程是线性的：

- 建立项目，登记受试者/实验对象与采集 Session
- → 导入原始记录（自动计算来源哈希，原始数据置为只读）
- → 自动质量控制与标准去噪
- → 查看清洗前后对照，必要时人工修订并冻结清洗版本
- → 选择一种主要分析方法或仿真方案
- → 提交任务，追踪进度与失败原因
- → 查看结果、警告与验证状态
- → 导出图表、数据表、报告与复现材料

有三条设计原则贯穿全流程，它们决定了这个产品和"一堆脚本的集合"的区别：

1. **一个工作流只跑一种具有独立科学含义的方法。** 每种方法有独立的方法 ID（含模态、估计器、profile 和版本）、独立的输入输出契约和测试。内部调用多个函数或生成多张图，不算多个方法。
2. **原始数据永不被覆盖。** 所有派生版本记录来源版本、参数、软件版本和哈希。
3. **"执行成功"、"方法成熟度"和"科学验证通过"是三个独立维度**，在产品里分别标注，不合并成一个"完成"状态。

## 3. 目标客户与他们的付费理由

| 客户类型 | 当前痛点 | 用了之后的变化 |
|---|---|---|
| 高校与科研院所实验室 | 分析方法随人员流动流失；每篇论文重做图表；返修时参数无法复原 | 标准流程固化在平台里，新成员按模板产出一致结果；参数与版本可直接调取 |
| 医院科研部门与临床研究团队 | 去标识化、权限、审计、保存周期的合规要求需要自建；临床采集数据的科研分析能力分散 | 合规要求内置在产品中；癫痫/睡眠/意识障碍/神经调控研究有标准工作流 |
| CRO、科研服务团队与独立分析团队 | 按项目承接分析，人力成本高、质量不稳定、成本难预估 | 批量项目走统一模板；成本可预估；交付物标准化 |

> **待补充**：这三类客户中，哪一类已经明确表达过付费意愿？为哪种交付物付费（分析任务本身／标准化报告／存储与备份／专家复核）？采购决策在课题组（用课题经费）还是在院所层面？这三个问题决定 §7 商业模式的具体形态，目前无法从产品逻辑推导。

## 4. 五条业务线

五条业务线各有独立的产品定义与成熟度判断，但共用同一套用户、项目、数据管理、任务执行与结果交付能力——不是五套产品，也不表示同时开发。

| 业务线 | 解决的科研问题 | 当前判断 |
|---|---|---|
| 神经电生理科研辅助分析 | 数据管理、EMG、ECG/HRV、睡眠分期、癫痫科研筛查、qEEG 19 导常模对比与报告导出 | 第一阶段首个交付目标；现有资产最成熟的部分 |
| 电生理分析 | scalp EEG、SEEG、ECoG 的专业分析工作流 | scalp EEG 在第一阶段内迁移；SEEG/ECoG 后续专项验证 |
| 电场仿真 | SimNIBS 个体头模与公共头模仿真，服务神经调控研究 | 第一阶段完成本地流程与技术验证 |
| Spike | 胞外电生理记录的 spike sorting、Unit QC、人工审核与下游分析 | 独立业务线，当前暂缓：不实现、不定价、不进入排期 |
| 原始数据备份存储 | 防止磁盘故障、误删除、设备丢失导致的科研数据永久丢失 | 第一阶段仅验证备份与恢复模型 |

几点需要说明的判断：

**为什么 Spike 单列且暂缓。** Spike 与 scalp EEG 虽同属电生理，但客户群体（动物电生理实验室 vs 人类脑电研究）、数据形态和处理链路（sorting + 人工 cluster 审核）差异都很大，作为电生理分析的子模态会拖累两边的产品定义。在获得合规的去标识化真实样本、能重新完成需求与技术评估之前，不进入任何阶段排期。

**为什么 SEEG/ECoG 不能跟着 scalp EEG 一起做。** 两者需要各自的电极模型（shaft/接触点 vs grid/strip）、参考方式、坏导与伪迹规则。仅因为能读取同样的文件格式就宣称支持，会产生"看起来正常但科学上无效"的结果。

**备份存储不是云存储或版本管理。** 它以备份集为单位，完成后其清单、哈希与策略快照不可改写，也不因其他存储的删除或损坏而级联删除。

平台分两层承载这五条线：公共层负责一致的数据、版本、安全与交付规则；专业服务层负责各领域的输入、QC profile、方法、参数与结果解释。公共层不能抹平专业差异。

## 5. 目前做到哪一步

这一节按项标注真实状态。**现有资产是分散在三个代码库中的分析能力，不是一个可交付的产品。**

| 能力 | 状态 | 说明 |
|---|---|---|
| 数据管理、EMG、ECG/HRV、睡眠分期、癫痫科研筛查（阈值+ML）、qEEG 19 导常模对比、报告导出 | **已验证可运行** | 在 pc-qlanalyser（PyQt5 桌面端）中长期使用，算法逻辑与报告版式经过实际数据检验 |

| 自动 QC、ICA/ICLabel、SafetyGate | **已验证可运行** | 在 qeeg-64ch-research 中已实现 |
| 统一项目版本模型、单方法工作流、结果契约、备份/恢复模型 | **已完成设计，未落地** | 设计约定已确立，尚未在统一产品中实现 |
| 统一的本地 Web 产品壳 | **未开始** | 第一阶段首个版本的核心工作 |
| SimNIBS 电场仿真集成 | **未开始** | 第一阶段第二个版本 |
| 云端协作、多租户、计费 | **未开始** | 需先完成本地验证 |

第一阶段的工作就是把上面"已验证可运行"的部分迁移进统一产品壳、完成产品级验收。在此之前，不宣称平台已具备完整的可交付能力。

## 6. 实施路线

### 6.1 第一阶段：本地验证与产品化

三个版本在**同一个**离线本地 Web 产品壳中顺序推进，不是三条平行分支。每个版本都必须用去标识化代表性样本完成技术可运行、科学数值/契约验证和端到端产品验收。

**版本1：神经电生理科研辅助分析 Web 化。** 迁移 pc-qlanalyser 已验证的算法逻辑，建立项目、数据版本、任务、报告、导出与本地备份/恢复模型。
*可演示成果*：从导入一份临床 EEG 到导出含图表、数据表、方法说明与复现材料的完整报告，全程离线，参数与软件版本可追溯。

**版本2：本地 SimNIBS 电场仿真。** 个体/公共头模输入检查、多套刺激参数配置、本地求解、多配置对比与复现交付。
*可演示成果*：同一头模下多套刺激方案的电场分布对比，并明确标注公共头模不代表个体分布。

**版本3：scalp EEG。** 迁移 web-main 已有方法，落地自动 QC、标准去噪、SafetyGate、清洗版本冻结复用与专业结果契约。
*可演示成果*：一份原始 EEG 经自动 QC 与去噪后的清洗前后对照，被阻断的数据明确给出阻断原因而不是伪装通过。

第一阶段全程不上云、不建设或启用收费系统。

### 6.2 云端阶段：满足条件后演进

云端阶段不与第一阶段无条件同步开发。只有当本地产品和拟上线的相应领域模块完成技术、科学及产品验证后，才启动对应云端能力与商业化准备。启动前至少检查：

- 本地端到端流程稳定；
- 方法与结果契约有证据；
- 安全和数据治理方案可实施；
- 目标客户和使用频率得到验证；
- 云资源与运维成本经过真实压测；
- 团队具备持续运营能力。

云端启动后的顺序是：先建设身份、组织、多租户隔离、在线上传、异步计算、审计和内部用量记录（usage ledger），再在账务一致性、退款/减免、容灾恢复与领域验证通过后考虑正式收费。**不以尚未验证的本地模块进行云端收费。**

## 7. 商业模式

### 为什么按任务收费，而不是订阅

科研经费是项目制的：课题组的钱绑定在具体课题和年度预算上。按分析任务收费能让费用直接计入某个课题预算，报销路径清晰。订阅制要求课题组预先承诺一段时间的固定支出，而科研分析的使用频率天然不均匀——投稿前密集、平时稀疏，这会让订阅在决策阶段就变成障碍。

### 候选收入结构

- 按分析或仿真任务收取服务费（主要来源）
- 按长期活跃存储、原始数据备份的容量与周期收费
- 超出套餐的下载流量
- 组织级服务（多成员、批量项目）
- 必要的实施、培训与专家复核服务

不同业务线可以共用账务基础设施，但不必共用同一计费单位：电生理分析按数据时长、仿真按单、存储按容量周期。

### 单位经济性（内部测算，非报价）

以阿里云公开标准价估算，一次 scalp EEG 分析（T4 级 GPU 约 15 分钟）的直接云成本在 0.5 元量级；一次 SimNIBS 个体头模求解在 3~5 元量级。相对内部价格假设，直接云成本占比很低。

**但这个比例不能当作利润率。** 它没有扣除人工复核、算法研发与维护、SimNIBS 许可证、数据库与监控、客服与销售、税费、失败重跑。定价必须覆盖全部成本，不能只看直接云成本毛利。详细测算见配套成本模型文档。

### 推进顺序

1. 先证明本地产品能稳定完成科研任务；
2. 再验证客户愿意为哪种交付付费；
3. 云端阶段先用 usage ledger 记录真实用量、不收费；
4. 积累真实用量后再设计收费、退款与优惠规则；
5. 正式报价基于真实压测、采购询价与客户访谈复核。

现有"5 元/数据小时/分析方法"、"SimNIBS 个体头模 2000 元/单、公共头模 200 元/单"等数字**均为内部测算假设，不是已确定的对外价格，也不构成报价承诺**。

## 8. 边界与合规

这一节不是免责声明，而是产品设计的一部分。对医院与临床研究客户，明确的边界是采购的前提条件。

**QLanalyser 不是临床诊断系统。** 不输出临床诊断或治疗建议。癫痫阈值/ML 科研筛查与 qEEG 19 导常模对比只能作为科研筛查参考，界面、报告与文档中必须保留"非诊断用途"提示。

**不夸大方法成熟度。** 不把生命周期未达 stable 的方法（draft / internal_validation / beta）包装为稳定临床结论；不把自动算法标签描述为已经人工确认。

**不跨模态外推。** 19 导常模不得外推为 64 导常模；scalp EEG 的参考、插值、ICA/ICLabel 与 QC 流程不得直接用于 SEEG/ECoG；公共头模结果不代表任何具体受试者的个体电场分布。

**数据安全。** 原始数据、患者数据与运行结果不进入 Git；密钥、令牌与授权信息不写入项目文件；用户应在上传前去标识化；文件名、报告与日志不得暴露患者身份；原始数据、派生数据与报告分别授权。医院科研数据的加密、访问控制与保存周期需专项确认。

**备份承诺的边界。** 第一阶段的本地备份仅代表"备份流程与恢复模型验证"，不构成设备级故障、磁盘损坏或场地灾难保护。在实现真实冗余、传输与静态加密、租户隔离、持续完整性监控与恢复演练之前，不使用"永不丢失、绝对安全、永久保存、零数据丢失、已实现跨地域灾备"等表述。RPO/RTO 当前未承诺。

## 9. 长期形态

长期目标是一套可从本地走向云端的综合科研平台，而不是本地版与云端版永久并行的两套产品。运行环境、存储、任务执行、身份与计费通过适配层替换，而同一项目模型、方法 ID、输入输出契约、ArtifactManifest 与版本追溯保持稳定。

平台成熟后应支持：跨机构协作，同时保持服务端强制的租户隔离（前端隐藏入口不构成安全边界）；覆盖 scalp EEG、SEEG、ECoG 与 Spike 的多模态分析，每种模态有自己的 QC profile 与解释规则；真实的数据保护能力——冗余、加密、隔离、持续完整性监控与恢复演练；方法生态按独立方法 ID 与生命周期管理，新方法上线不影响既有结果的可复现性。

> **待补充**：三年期的量化目标（服务多少个课题组／覆盖哪些模态／是否开放第三方方法接入）。这需要结合市场验证结果确定，目前不设数字。

## 10. 风险与待决策

### 主要风险

| 风险 | 应对 |
|---|---|
| 科研功能被误解为临床诊断 | §8 的边界写入产品界面与报告，不只写在文档里 |
| 不同模态错误复用同一 QC/参考/解释规则 | 每种模态建立独立 profile，未通过真实样本验证不进入可用状态 |
| 迁移历史代码库时形成第二套产品壳或不可追溯旁路 | 统一产品壳约束；历史功能先登记对照再决定合并或归档 |
| 本地流程尚不稳定就投入云端商业化 | §6.2 的启动条件清单；不以未验证模块收费 |
| 备份模型验证被误宣传为真实容灾 | §8 的措辞禁令；RPO/RTO 未演练不承诺 |
| 内部价格假设只覆盖直接云成本 | §7 明确全成本口径；正式报价前重新询价 |
| 五条业务线同时展开导致资源分散 | 顺序推进；Spike 明确暂缓 |

### 待决策

1. **云端启动条件**：本地产品达到什么稳定度；每个领域模块需要哪些证据；需要多少真实用户/项目验证；由谁做启动评审。
2. **第一阶段聚焦与命名**：版本1 业务线正式名称；新产品壳技术栈；历史 SQLite 数据迁移；本地默认目录；各代码库交接方式。
3. **科学交付门槛**：首批开放哪些工作流；哪些必须人工复核；普通/专家参数权限；PDF、中英文方法说明与投稿图范围。
4. **SimNIBS 条件**：本地部署、许可证、输入格式、头模边界与算力条件。
5. **SEEG/ECoG 顺序**：本地模态验证与云端适配的先后；首批真实样本、专业顾问与验收标准。
6. **云端治理与商业化**：医院数据安全要求；PI 非自愿失效的应急接管；计费精度；SafetyGate 阻断结算；存储/流量/备份计费与退款规则。
7. **备份服务承诺**：恢复权限与路径；真实冗余；完整性检查；RPO/RTO 与演练要求。
8. **Spike 重启门槛**：维持暂缓；仅在获得合规真实 PLX 样本、确认客户问题并具备专项资源后重新立项。
