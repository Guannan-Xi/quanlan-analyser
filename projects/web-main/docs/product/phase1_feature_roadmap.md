# QLanalyser 第一阶段功能清单与架构重构路线图（简化版）

- 状态：草案，待架构组评审
- 日期：2026-07-24（简化改写）
- 说明：这是给非技术背景也能看懂的版本。工程/算法团队做排期时，请参考同目录的详细版（含具体文件路径、行号、算法细节），本版只讲清楚"做什么、先做哪个、谁要决定什么"。

## 这份文档在说什么

QLanalyser 第一阶段要把现有的分析方法、自动质检（QC）和后台架构做一次系统性梳理和升级。这份文档基于对代码库的实际核查（不是猜测），列出：

1. 第一阶段要交付哪些分析功能
2. 新增的"自动质检"要怎么做，卡点在哪
3. 后台架构要怎么改，分几步走
4. 有哪些事情现在**必须先有人拍板**，否则后面没法排期

## 六项已确认的决策

1. 账户/计费/云存储这些"超前做好"的功能——先留着，不删，但第一阶段不对外开放。
2. 自动质检/去噪——走成熟的现成工具（pyprep、ICA/ICLabel、autoreject），不自己重新发明算法。
3. "微状态"分析纳入第一阶段；其他几个更细的指标（GFP/GMD、复杂度、Aperiodic谱）往后放。
4. SimNIBS仿真往后放，不影响第一阶段。
5. 后台架构第一阶段必须完成重构（用"配置驱动"代替现在的硬编码）。
6. 这份文档就是把以上决策落地成具体清单。

**一个好消息**：原本以为"自动质检的核心算法（坏导检测、ICA、SafetyGate安全门）整个代码库都没有，要从零写6-9周"，实际核查后发现**大部分已经有真实代码实现**，只是在另一个项目（qeeg-64ch-research）里，还没搬到主线（web-main）。这大幅降低了工作量和风险。

## 第一阶段要交付的分析功能

现有9个对客户开放的分析方法（PSD、Band Power、ERP、TFR、Multitaper、PAC v1/v2、Connectivity、Reference/CSD，加上新增的"微状态"）都要**补接一个新的自动质检+安全门流程**——目前它们都是直接吃原始上传文件，还没有经过自动质检这一步。这9个方法工作量基本同等，需要一起排期，不能因为"已经实现"就以为没有新增工作量。

## 自动质检要怎么做（新增能力）

自动质检整体像一条流水线，按顺序做这几件事：

1. 找出信号质量差的电极（坏导）
2. 把找出来的坏导用周围电极的数据"修补"回来（插值）
3. 滤波，去掉工频干扰和不需要的频段
4. 用ICA算法把眼动、心跳等干扰成分识别出来
5. 自动判断这些成分能不能被安全剔除（ICLabel）
6. 把质量太差的时间段剔除
7. 综合以上结果，给出"可以自动通过"或"需要人工复核"的结论

这条流水线的**大部分步骤已有现成代码**，只是分散在另一个项目里，需要搬过来、修一个已知的小bug（平均参考计算时误排除了已经修补好的电极，会让部分测量结果整体偏移）。

**三个必须先拍板的问题**（否则没法排期）：

- **问题A：现在的后台是同步执行的，跑一次自动质检可能要几十秒到几分钟，会不会导致网页请求超时？** 需要决定：现在就上"后台任务队列"，还是先接受同步、但加个超时和进度条。
- **问题B：自动质检的关键一步（ICLabel自动分类）依赖"电极位置信息"，但很多上传的数据可能没有这个信息。** 没有电极位置信息时，这一步会自动判定失败、转人工复核，导致"自动通过"的比例可能远低于预期。需要决定：要不要在上传阶段就想办法补全电极位置信息（比如默认套用标准模板），还是接受"没有电极位置信息的数据大概率要人工复核"这个现实。
- **问题C：几个分析方法（PSD、微状态、Connectivity等）在计算时，如果数据中间被质检流程"掐掉"了一段，直接拼起来算可能会产生错误结果（比如误判成信号突变）。** 需要决定：每个方法是要"跳过被掐掉的部分再分段计算"，还是"换一种不受影响的计算方式"。这个决定会影响具体的开发工作量，需要算法组逐个方法确认。

## 后台架构要怎么改

现在的后台有三块比较"硬编码"、不好扩展的地方，第一阶段要按风险从低到高分三步改：

1. **工作流配置**：现在新增一个分析方法要改代码里的固定列表，改完后应该变成改一个配置文件就行。
2. **存储方式**：现在"存本地"和"存云端"的逻辑写在一起，改完后要能像插拔一样切换存储方式，不用改业务代码。
3. **任务分发+数据版本管理**：现在派发分析任务是一长串if/else，改完后要变成"按方法名查表分发"；同时要新增"清洗版本"这个概念，让同一份数据的同一次清洗结果可以被复用，不用每次都重新跑质检。

这部分改动风险可控，可以和自动质检的开发并行推进，但"任务分发"要等自动质检的方案确定之后才能真正接上。

## 微状态迁移要注意的点

微状态分析的核心算法（KMeans聚类+分类）已经在另一个项目里验证过，可以直接搬过来，不用重新写。但有两点要注意：

- 现成代码是"从头到尾连续计算"的，如果数据中间被质检流程掐掉了一段，需要改造成"跳过被掐掉的部分"，这个改造量要等上面"问题C"的决定才能定。
- 现成的验证数据（用来对比迁移后数值有没有错）本身可能受那个"平均参考bug"影响，用之前要先确认这份验证数据干不干净，不能拿一份可能本身就有问题的旧结果去验证新代码对不对。

## 明确不做的事

- 不删除现有代码，包括"超前做好但暂不开放"的账户/计费/云存储等功能。
- GFP/GMD、复杂度指标、Aperiodic谱、SimNIBS仿真、SEEG/ECoG专项分析、Spike排序——这些都往后放，不影响第一阶段。
- 这次只是产出文档、做只读核查，没有改动 `pc-qlanalyser`（桌面版）或其他任何代码。

## 三个待拍板问题一览（需要有人给出决定和完成时间）

| 问题 | 谁来决定 | 影响 |
|---|---|---|
| A：同步执行会不会超时，要不要上任务队列 | 架构组 | 决定自动质检能不能稳定跑完 |
| B：没有电极位置信息的数据怎么处理 | 产品+算法组 | 决定"自动通过"比例，以及是否要补做上传阶段的电极位置匹配功能 |
| C：几个分析方法怎么应对被质检掐掉的数据片段 | 算法组 | 决定微状态等方法的具体改造工作量 |
